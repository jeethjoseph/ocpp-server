# Late StopTransaction records the truth without moving the money

Status: done

## What to build

A `StopTransaction` arriving for a **Charging Session** the CSMS has already finalized and invoiced must not rewrite the figures the money was computed from.

Today the stop handler unconditionally overwrites end meter, energy, end time and status, then re-runs the billing chain. The downstream money paths are each individually idempotent, so there is no double refund or double invoice — but the transaction row is silently rewritten. After a write-off finalized at 0.4 kWh, a late stop reporting 22 kWh leaves the **GST Invoice** saying 0.4 kWh and the session it points at saying 22 kWh, with nothing explaining the gap and no credit-note mechanism to correct it.

Add a terminal-state guard so the billed fields are immutable once finalized, and record what the charger reported in separate reported-only fields alongside the existing `reported_end_time`. Emit an audit event and an alertable custom event so the frequency is measurable — this is the figure that says what the write-off policy is actually costing.

**The guard covers `MeterValues` too, not only `StopTransaction`.** After the sweep writes a session off, the charger can reconnect and replay hours of queued `MeterValues` frames for a transaction that is now terminal. Today `on_meter_values` auto-resumes only `SUSPENDED` and otherwise proceeds as if the transaction were live — so a replay against a finalized row would store readings, run the budget check, and could schedule a `RemoteStop` for a session the books already closed. Frames for a terminal transaction must be accepted on the wire (the charger needs its `MeterValues.conf` to drain the queue), stored as readings for forensics, and excluded from every billing and budget path. The last replayed reading is what feeds the reported-only fields when no late `StopTransaction` follows.

This is the **only remaining server-side prerequisite** for [[offline-charging-continuity]]: without it, firmware that keeps the contactor closed will routinely produce late stops that corrupt the invoice register. Nothing on the firmware side should ship before it.

See ADR 0031 decision 5, and the **Reported energy vs Billed energy** entry in CONTEXT.md.

## Acceptance criteria

- [x] A `StopTransaction` for a transaction in a terminal state leaves `energy_consumed_kwh`, `end_meter_kwh`, `end_time` and `total_billed` unchanged
- [x] The charger's reported energy and meter reading are persisted to reported-only fields
- [x] No second invoice, refund, settlement entry or wallet debit is produced
- [x] An audit event and an alertable custom event are emitted, carrying the gap between reported and billed energy
- [x] A late stop for a still-open transaction behaves exactly as today (no regression)
- [x] `MeterValues` for a terminal transaction are acknowledged and stored, but do not resume the session, run the budget or balance check, schedule a `RemoteStop`, or touch billed fields
- [x] `MeterValues` for a `SUSPENDED` or `RUNNING` transaction behave exactly as today
- [x] Migration is generated by Aerich, not hand-written
