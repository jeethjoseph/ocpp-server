# Bundle identity becomes SHA-256 of the body, replacing (epoch, bundle_seq)

Status: done

## What to build

Idempotency currently keys on `(charger_id, epoch, bundle_seq)` plus a header content comparison. That mechanism is actively broken in the field: the staging unit reused `seq=4` across four bundles covering four different record windows, so every upload read as a reflash and opened a new epoch.

Replace it with a content hash, which needs no firmware state and cannot be confused by a reused sequence number.

- Add `content_sha256 = fields.CharField(max_length=64)` to `DiagnosticBundle`, with `unique_together = (("charger", "content_sha256"),)`.
- Compute over the **raw received** body (post-gunzip, pre-redaction), **excluding a leading `#VLTDIAG/` line if present**.

Both details are load-bearing and neither is optional:

  * **Exclude the legacy header line from day one**, not once the firmware stops sending it. Three consecutive retries of one logical bundle in staging were byte-identical across all 460 body lines and differed *only* in the header's `last=` field, producing three different digests. Hash the header in and nothing ever dedupes — and the bug passes synthetic fixtures while failing on real traffic, because fixtures repeat the header verbatim and real retries do not.
  * **Hash the raw body, not the redacted one.** Identity answers "has this charger sent me these bytes before", which must be stable against our own policy. Hashing post-redaction means adding one redaction pattern rotates every historical digest and makes every old retry look new. Store the raw digest for identity; S3 still holds the redacted bytes.
- `diagnostic_bundle_service.record_bundle` looks up by `(charger, content_sha256)`. A hit returns `(existing, False)` and the caller returns 2xx with the original `s3_key`, unchanged from today's duplicate behaviour.
- Keep the `IntegrityError` catch for the concurrent-upload race; it now guards the hash uniqueness constraint instead of the sequence one. The reasoning in that comment still applies verbatim.

Leave the header parsing and the old columns alone in this issue — they are removed in issue 05. This slice only changes what identity means, so it can land and be verified on its own.

Migration must be generated by Aerich (`docker exec ocpp-backend aerich migrate`), not hand-written. If Aerich prompts about unrelated renames, that is stale-local-DB drift — run `aerich upgrade` first and retry.

## Acceptance criteria

- [x] `content_sha256` column added via an Aerich-generated migration, unique per charger.
- [x] Hash is computed over the raw received body with any leading `#VLTDIAG/` line stripped.
- [x] Regression test using the three real staging retries (identical bodies, differing `last=`): all three must hash equal and produce exactly one row and one S3 object.
- [x] Changing a redaction pattern does not change the digest of a previously-seen body.
- [x] Re-POSTing an identical body returns 2xx with `recorded: false` and the original `stored_key`, and writes no second S3 object.
- [x] Two bundles with the same `seq` but different content are both stored as distinct rows (the case that currently inflates epoch).
- [x] Concurrent identical uploads resolve to one row via the `IntegrityError` path, no 500.
- [x] Tests cover: exact retry, same-seq-different-content, concurrent race.
- [x] `docker exec ocpp-backend pytest tests/test_diagnostic_bundle_service.py tests/test_diagnostics_endpoint.py` passes (baseline: 63 passed across the five diagnostics files).
