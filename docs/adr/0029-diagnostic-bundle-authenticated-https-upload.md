# Chargers push Diagnostic Bundles over authenticated HTTPS, outside the OCPP channel — and that endpoint ships the Charger Auth Key ahead of ADR 0020

Charger-side firmware debug traces reach the CSMS as **Diagnostic Bundles**: opaque blobs POSTed by the charger to `app.voltlync.com` over HTTPS, authenticated with **HTTP Basic Auth** using the per-charger **Charger Auth Key**, and stored in S3. OCPP `GetDiagnostics` is deliberately **not** used, and neither is vendor `DataTransfer`. Uploads run **nightly with per-charger jitter plus on fault**, and every bundle carries a header — sequence number, record range, and a monotonic overflow counter — so that **data loss is visible rather than silent**. This endpoint is the **first consumer** of the Charger Auth Key: the credential specified by [ADR 0020](0020-charger-websocket-basic-auth.md) is provisioned fleet-wide as part of this work, while the OCPP WebSocket handshake **remains unauthenticated** for now.

## Context

Chargers accumulate internal firmware debug traces — boot messages, state-machine transitions, modem/AT failures, relay actuations, vendor fault detail — that the CSMS currently never sees. The **OCPP message log** captures only protocol traffic the server itself observed, which is the wrong side of the wire for diagnosing "why did this unit fault at 14:32".

**OCPP 1.6 does provide a mechanism, and we rejected it.** `GetDiagnostics` + `DiagnosticsStatusNotification` is the in-spec answer, but it does not survive contact with this hardware:

- The charger's on-board memory is a **2 Mbit (256 KB) I²C EEPROM** (STMicroelectronics M24M02 class — 256-byte pages, block write-protect, a permanently-lockable identification page). It is a **configuration and identity store, not a filesystem**. `GetDiagnostics` responds with a *fileName* and uploads a *file*; there is no file here, and per spec a charger with nothing to offer returns `GetDiagnostics.conf` with no filename at all — a conformant no-op.
- `GetDiagnostics` puts a **directory URI** in `location` and the charger appends its own filename, which invalidates any S3 presigned-PUT signature.
- OCPP 1.6 only mandates **FTP/FTPS** for that upload; HTTP support is vendor-optional.

The firmware team independently committed to buffering traces in EEPROM and **uploading them periodically over HTTP** — no `GetDiagnostics` call needed. That is a simpler contract than the spec mechanism and we accepted it.

Two facts then forced the remaining decisions:

**The archive model rules out `DataTransfer`.** A **store-and-forward** design (drain small batches continuously over the open WSS, like `SignalQuality`) was considered and lost to the firmware team's **archive** model (accumulate, upload in bulk). Given bulk, `DataTransfer` is disqualified on storage: every inbound `DataTransfer` is written to the `log` table *with its payload* and held for the full 90-day `RETENTION_DAYS` window. At ≤192 KB per charger per day across ~30 chargers, base64-inflated, that is roughly **690 MB added to `log`** — against a staging database whose entire RDS-cutover dump was 469 MB, and against the table [ADR 0014](0014-logs-console-bounded-query-surface.md) already exists to keep queryable. A 192 KB archive also does not fit one OCPP frame, so it would require a chunking and reassembly protocol layered over an RPC channel.

**There is no charger credential today.** ADR 0020 specifies the Charger Auth Key but is explicitly `PROPOSED — NOT YET IMPLEMENTED`: there is no `Charger.auth_key_hash` column and chargers connect to the OCPP WebSocket unauthenticated. An HTTPS endpoint, unlike a WSS connection, has no ambient identity to inherit — so this feature had to solve authentication from scratch or invent a throwaway secret.

## Decision

**Transport.** The charger POSTs a Diagnostic Bundle to `POST /api/diagnostics/bundles` on `app.voltlync.com`, behind the existing nginx (whose `client_max_body_size` is already 100M). The backend streams the body to S3. Charger-facing routers follow the `/api/<thing>` convention already set by `firmware.public_router`; the admin surface lives under `/api/admin/diagnostics`.

Same host and same Let's Encrypt certificate the fleet already validates on every WSS reconnect — so no new TLS trust path is introduced. Pointing `location` at a raw S3 URL was rejected partly for this reason: `s3.ap-south-1.amazonaws.com` presents an **Amazon Trust Services** chain the fleet has never been proven to trust, and embedded trust stores are frequently stale.

**Bundle header — loss must be visible.** Every bundle carries a small fixed header ahead of the opaque body:

- a **bundle sequence number**, incremented per upload and persisted across reboot;
- the **record range** the bundle covers (first and last record number);
- a **monotonic overflow counter** — the running total of records the ring buffer overwrote *before they were uploaded*.

Under the archive model, silent data loss is otherwise the **default behaviour**, and it fails worst exactly when it matters most: a charger that starts faulting logs far harder than usual, wraps its buffer within hours, and delivers a bundle containing only the tail of the retry noise with **no indication the root cause was overwritten**. A reader would date the fault to the start of the bundle and be wrong. The second, quieter case is an upload that fails and never retries — bundle N and bundle N+2 arrive with no marker that anything sits between them.

The header makes both **visible and alertable**, and — this is the point — **tells them apart**. A gap with `overflow = 0` means a bundle never arrived (network/retry problem). A gap with `overflow > 0` means the buffer wrapped (the charger logged faster than it uploaded). Same symptom, opposite remediation.

The counter is **monotonic**, never reset, wrapping at 32 bits; the server diffs against the previous bundle's value. Resetting it after each successful upload was rejected: the reset variant loses its own evidence in precisely the case that matters, because a missing bundle takes its overflow count with it, and the loss becomes invisible again.

**Delivery is acknowledgement-based, and the server acks only on durability.** The charger advances its delivered marker **on HTTP 2xx and nothing else** — not on a successful connect, not on a timeout, not on a 4xx. Anything else leaves the records unread so the overflow counter keeps counting them honestly. Retry is two backoff attempts (~+15 min, ~+60 min) then wait for the next scheduled cycle; a server down for a day must not burn a day of cellular data, and the overflow counter reports afterwards whether anything was actually lost. A 4xx means *stop retrying now*, never *discard* — a 401 from a botched key rotation must not cost the buffer.

Correspondingly, **the backend does not return 2xx until the object is durably in S3**. Accept the body, complete the `put_object`, then respond; on S3 failure return 503 so the charger keeps the records. Acking on receipt and writing asynchronously would tell a charger "delivered" for data that no longer exists anywhere.

**Bundle identity, and the sequence-reset case.** Uniqueness is `(charger_id, epoch, bundle_seq)`; a re-sent bundle already stored returns 2xx without rewriting, which closes the routine "S3 write succeeded, response lost on cellular" case. `charge_point_string_id` is a UUID4, so this cannot collide across environments the way the per-DB integer keys behind `qr_payment_{PK}` did.

The **epoch is assigned by the server, not the firmware**. A reflash, EEPROM clear, or botched provisioning sends `bundle_seq` back to 1, and under a naive unique constraint the charger's new data would be silently dropped as duplicates — the worst outcome for a loss-detection system. No firmware-side value can prevent this (nothing in the EEPROM survives an EEPROM clear), so the server detects it instead: an incoming `bundle_seq` at or below the last seen for that charger increments a server-held epoch and is recorded as an event. The detector is unambiguous because at one bundle per day even a 16-bit counter takes ~179 years to wrap, so any backwards movement is a genuine reset rather than a wraparound.

**Limits.** Body capped at 2 MB via an env var — well above today's ~192 KB and raisable without a code change should the fleet move to SPI NOR flash — and ~6 uploads/hour per charger, leaving headroom for retries and repeated fault-triggered uploads while bounding a runaway.

**Cadence: every 6 hours with jitter, plus fault-triggered.** The charger uploads **four times a day at approximately 6-hour intervals**, with each unit's offset within its window derived deterministically from its `charge_point_string_id` so ~30 chargers do not hit the endpoint on the same minute.

Six hours rather than nightly is forced by a **hard 48-hour backdating limit on New Relic's Log API**, measured against the live account (§Consequences). A nightly bundle's oldest records are ~24h old at upload — inside the window — but a *failed* nightly cycle falls through to the next night, putting them at ~48h where they begin disappearing from the index. A 6-hour cadence keeps every record far inside the window even after a failed cycle, at identical total bytes and merely more requests. If the firmware team can go faster still, nothing here objects.

It **also uploads shortly after entering a fault state**, guarded by a firmware-side minimum interval (~15 min) so a unit stuck in a fault loop does not upload continuously; the ~6/hour server-side rate limit backstops it. This is the higher-value half: the failure mode the overflow counter *detects* — a charger faulting at 15:00 and drowning its own root cause in retry noise before the nightly upload — is one that fault-triggered upload largely *prevents*.

**No server-initiated flush (deferred, not rejected).** An admin cannot pull a bundle on demand. This was specified as `DataTransfer(vendorId="VoltLync", messageId="FlushDiagnostics")` and needs **zero new server machinery** — outbound `DataTransfer` already ships (`main.py:401` sends `PostBootState`; `connection_manager.py:369` dispatches the action) — but the firmware team declined the inbound `messageId` branch for this release. Note it is far cheaper than the `GetDiagnostics` they also declined: no `location` parsing, no file semantics, no FTP client, just an "upload now" nudge to a charger that already knows how to upload. Revisit when firmware capacity allows; nothing here blocks it.

**Storage and indexing.** The blob goes to a **dedicated per-environment S3 bucket** (`AWS_S3_DIAGNOSTICS_BUCKET`), separate from the firmware and invoice buckets. The separation is deliberate rather than tidiness: Bundles carry a 90-day lifecycle rule where firmware images are kept indefinitely and invoices are retained for compliance, and Bundles may contain charger-side PII, so they warrant their own access policy. Provisioned 2026-08-18 as `voltlync-diagnostics-staging` (ap-south-1): all public access blocked, AES256 default encryption, a TLS-only bucket policy, and a 90-day expiry rule. The EC2 instance role `OcppServerEC2Role` gets an inline `VoltlyncDiagnosticsS3Access` policy granting Get/Put/List but **not** Delete — the lifecycle rule expires Bundles and the application can never remove one. The prod bucket is not yet created; the policy already covers its ARN, so it needs no IAM change. Objects land under a per-charger, date-partitioned prefix (`diagnostics/{charge_point_string_id}/{YYYY}/{MM}/{DD}/{epoch}-{bundle_seq}.bin`), following the `build_firmware_s3_key` precedent. A small `DiagnosticBundle` row is the queryable index — charger FK, epoch, sequence, record range, overflow count, S3 key, byte size, `received_at` — roughly one row per charger per day. Retention is an **S3 lifecycle rule at 90 days**, matching the `RETENTION_DAYS` doctrine already applied to the `log` table: Bundles are disposable observability data, and the consistency matters more than the (negligible) cost either way. The first header byte is a **format version**. The body is **newline-delimited text**, and is parsed rather than stored opaquely — see below.

**Fan-out on ingest: the file is archived, the lines are indexed.** One upload produces **two** artifacts answering two different questions, and neither substitutes for the other:

- the **raw bundle in S3** plus its `DiagnosticBundle` row — the archive of record and the index *of bundles*, answering *"did I receive everything from this charger?"* via sequence numbers and the overflow counter;
- the **individual log lines**, parsed and forwarded to **New Relic Logs**, tagged with charger code, station, bundle sequence, and severity — the index *of lines*, answering *"what actually happened?"* across the fleet.

Storing the bundle as an opaque blob was the initial default and is **rejected**. The most valuable questions are fleet-wide — *"which chargers show this AT failure?"*, *"did the four units that faulted last week share a signature?"*, *"alert me when any charger logs `WATCHDOG_RESET`"* — and a blob-per-charger archive answers **none** of them; you would download thirty files and grep locally. S3 treats object contents as an opaque byte stream, and device-blob archives reliably become write-only for exactly this reason.

This is the Loki architecture (index labels, keep content cheap in object storage) implemented on a platform already in use. **Cost does not drive this decision at this scale** — ~30 chargers × ≤192 KB/day is ~175 MB/month, which is **0.17% of New Relic's 100 GB/month free allowance** on the account already ingesting from both environments; S3 is pennies and Athena queries would be about a cent. Every option is effectively free, so the choice is made on query capability and operational effort, where New Relic wins decisively: no new infrastructure, **no viewer to build**, and traces land in the same query surface as `OCPPWebSocketDisconnect` events, so *"the charger dropped WSS at 14:32 — what was the firmware doing?"* is one query rather than two systems.

Four ingest rules, each guarding a failure that is silent otherwise:

- **Forwarding must not gate the 2xx.** S3 is the durability contract; the line index is a derived view. If New Relic is unreachable, store, return 200, and replay the fan-out from S3 later — otherwise a vendor outage makes chargers re-upload data already safely delivered.
- **Charger clocks are anchored but not always right.** Each line carries a wall-clock timestamp, and units set their RTC from `BootNotification.currentTime` — so the fan-out has a real time axis and traces correlate against `OCPPWebSocketDisconnect` events. Two gaps remain. Lines written **before the first successful BootNotification** carry an unset or stale RTC, which is worst precisely where it hurts most: a charger that cannot reach the server logs its connection failures with a garbage clock. A `CLOCK_SET from=<old> to=<new>` marker line lets the server retroactively shift that boot segment by the delta; without it the pre-connection window is permanently untimed. Separately, setting time only at boot lets a cheap RTC drift seconds per day, so a long-uptime charger runs minutes off — re-syncing from `Heartbeat.conf`'s `currentTime` bounds drift to the heartbeat interval at no cost. Regardless: index on charger time, carry server receipt time alongside, and flag implausible skew.
- **Never drop an unparseable line.** Forward it raw with a `parse_failed` flag. Firmware format drifts, and a silent drop means a firmware update deletes your logs with nothing reporting it.
- **Keep label cardinality low.** Charger code, station, and severity are labels; message content and transaction IDs are not.

**Admin surface.** Line-level search is **New Relic's UI — we build none**. What we build is a panel on the charger detail page listing recent Bundles with overflow/gap columns and a presigned download link, following the Firmware Library precedent: that surface exists to answer *delivery* questions and to retrieve raw bundles older than New Relic's retention window, not to read traces. It is **not** the **Logs Console**, which is a view over the `log` table (ADR 0014) and shares no schema with this. `received_at` is stored UTC and rendered IST per the repo timestamp rule. A non-zero overflow delta or a detected sequence gap emits an **NR custom event** so both are alertable without reading a trace.

**Authentication.** HTTP Basic Auth, username = `charge_point_string_id`, password = the **Charger Auth Key** — byte-for-byte the scheme ADR 0020 specifies, applied to HTTPS instead of the WSS handshake. Server stores only a SHA-256 hash in `Charger.auth_key_hash`; plaintext is revealed once at provisioning; lost key ⇒ rotate, never retrieve.

**Not client certificates.** mTLS (OCPP Security Profile 3) was rejected: it obliges us to run a CA with issuance, renewal, and revocation, and its dominant failure mode at this fleet size is **an unnoticed expiry taking chargers dark in the field** — a larger operational risk than the compromise it mitigates. The threat being defended against is modest: a stolen upload secret buys an attacker the ability to POST junk debug traces for one charger. No billing, control, or customer-data exposure.

**Sequencing — deliberate and partial.** This work ships the *credential* half of ADR 0020 (column, provisioning, rotation, admin reveal-once surface) and uses it **only** for bundle upload. The OCPP WebSocket handshake **stays unauthenticated**; ADR 0020 remains PROPOSED. The timing argument is the whole reason: the firmware team must touch every unit anyway to add bundle upload, so loading a 20-byte secret at the same moment is nearly free, whereas a separate provisioning campaign later means revisiting a fleet of flaky-modem chargers in the field. **The marginal cost of the credential is near zero now and rises permanently after this deployment.**

**Enforced from day one on this endpoint.** Unlike the WSS path, there is no installed base to migrate, so an upload from a charger with a null `auth_key_hash` is rejected outright. ADR 0020's per-charger legacy-mode grace does **not** apply here.

## Consequences

- **The WSS spoofing exposure documented in ADR 0020 stays open.** Knowing a `charge_point_id` is still sufficient to impersonate a charger on the OCPP connection and inject `StartTransaction`/`MeterValues`. Accepted deliberately: this ADR narrows the *remaining* work on 0020 to a handshake check against an already-populated column, but it does not close the hole.
- **The Charger Auth Key's blast radius grows later, not now.** Today a leaked key buys junk bundles. Once 0020 ships on the same credential, it buys full charger impersonation. One key for both channels is still correct — it is the same secret on the same chip either way — but server-side handling must be careful from the start: constant-time comparison (`hmac.compare_digest`), and the `Authorization` header must never be logged (cf. the prod `DB_PASSWORD` leak recorded in `feedback_no_secrets_in_ssm_params`).
- **This feature carries scope it did not ask for.** Per-charger credential provisioning, rotation, and a reveal-once admin surface are now part of a logging feature. That is the price of the timing argument above.
- **The endpoint is public and accepts arbitrary bytes.** It needs a size cap and rate limiting independent of authentication.
- **On the charger, the Auth Key belongs in the EEPROM's write-protected config block.** The M24M02's block write-protect (¼ / ½ / whole) is what stops a runaway log-buffer pointer from destroying the charger's own credential — the difference between "logging bug loses logs" and "logging bug bricks authentication". Config and identity in the protected region, the trace ring buffer in the remainder.
- **EEPROM write endurance is a firmware-side risk we do not control.** The part is rated >4M cycles at 25 °C but **1.2M at 85 °C**, and endurance is per-page. A wear-levelled circular buffer is comfortably fine; a write pointer kept at a fixed address is not — at one entry per second it fails in about two weeks, silently, in the field. The firmware team must confirm the head pointer is wear-levelled.
- **A non-zero overflow count is a standalone alert signal.** It says a charger suddenly started logging much harder than normal, which nearly always means it is in trouble — actionable before anyone reads a trace line, and independent of bundle content.
- **The overflow counter settles the buffer-sizing question empirically.** Nobody currently knows whether ~192 KB of usable EEPROM holds a day or an hour of this firmware's output. Routinely zero ⇒ the EEPROM was sufficient. Routinely large ⇒ that is measured production evidence for moving logs to a separate ~16 MB SPI NOR flash part, rather than an argument from first principles.
- **Without a server-initiated flush, a misbehaving-but-not-faulting charger is invisible until the next nightly window.** Slow charging, intermittent drops, a customer complaint on a unit that never enters a fault state — none of these trigger an upload. Fault-triggered upload covers the incident case, not the "something is off" case. This is the main capability given up by declining both `GetDiagnostics` and the flush command.
- **New Relic's Log API silently drops records with timestamps older than 48 hours.** Measured on account 7468195: a control record and one backdated 30h both landed (with the backdated timestamp preserved); one backdated 60h did not. **All three returned `HTTP 202 Accepted`** — the drop happens downstream and is invisible from the ingest response. This is why the cadence is 6-hourly. It also means the server **MUST compute record age and mark anything beyond ~47h as archive-only** on the `DiagnosticBundle` row, so the admin surface can say *"records before X are in S3 only"* rather than presenting a quietly incomplete index. A charger offline for more than two days will have its entire backlog land in S3 and never in New Relic.
- **Retention is settled by measurement, not choice.** The `Logging` namespace on the account caps at **30 days**; the S3 lifecycle rule is 90. That is the hot/cold split: search recent records in New Relic, retrieve the raw bundle from S3 beyond it.
- **Headroom is confirmed ample.** Current total ingest is ~30.9 GB/30d (Tracing 10.6, Metrics 9.5, Logging 9.4, APM 0.8, Browser 0.6) against the 100 GB free tier. Diagnostic Bundles add ~175 MB/month — **0.2% of the tier**. The account already ingests Logs from `OCPP-Server-Production` and `OCPP-Server-Staging`, so the product is live and no new integration is needed.
- **Fan-out must use the Log API directly, not the Python APM agent.** The agent's log forwarding cannot set a historical timestamp, and these records are hours old by construction. POST to `log-api.newrelic.com/log/v1` with an explicit `timestamp` field. Batch at ~500 records per request with gzip: the API caps a payload at **1 MB**, and a full bundle is ~500–600 KB of JSON once attributes are attached — it fits, but without much margin.
- **Bundles are disposable by construction.** Because they are diagnostic-only, retention can be aggressive and durability requirements are low. See the `CONTEXT.md` **Diagnostic Bundle** entry for the non-metering exclusion, which is load-bearing: a second, unaudited copy of energy data would put this stream adjacent to GST invoicing and settlement, and it deliberately is not.
- **If these units carry BG95/BG96 modems, each upload will drop the OCPP WSS connection** — the single-TLS-context limitation already documented for firmware downloads. Mitigation is known (schedule uploads in the IST small hours; reuse `firmware_update_service._mark_ws_drop_expected` so the disconnect does not fire `charger.disconnected` audit events and `OCPPWebSocketDisconnect` NR events). **The modem model is not yet confirmed** and should be before implementation.

## Considered alternatives

- **OCPP `GetDiagnostics`** — the in-spec mechanism. Rejected: the hardware has no filesystem to produce a diagnostics file, the `location` directory-URI semantics break presigned S3 URLs, and 1.6 only mandates FTP/FTPS. The firmware team does not implement it and would have to.
- **Vendor `DataTransfer`, following the `SignalQuality` precedent** — reuses an authenticated channel and a pattern the firmware team has already shipped, and inherits charger identity for free. Rejected under the archive model on storage cost (~690 MB added to the 90-day `log` window) and the chunking protocol a 192 KB payload would require. **Would have been the right answer under a store-and-forward model**, and is worth revisiting if the firmware team ever moves to continuous drain.
- **Store-and-forward instead of archive** — drain small batches continuously while online, using EEPROM only to survive disconnection. Better on nearly every axis: near-zero EEPROM wear, no bulk transfer, no chunking, and traces arriving within minutes instead of the next day. Not chosen — the firmware team had committed to the archive model. Its one genuine advantage is that bulk upload keeps this stream entirely off the OCPP path and out of the `log` table.
- **A raw buffer dump with no header** — what the firmware plan implied. Rejected: an observability stream whose completeness cannot be checked is worse than none, because confident wrong conclusions get drawn from it.
- **A per-bundle overflow counter that resets on successful upload** — reports only that bundle's losses. Rejected as fragile in the one case that matters; see Decision.
- **Opaque blob archive with a per-charger download link, no parsing** — the initial default here. Rejected once the body was confirmed to be text; see Decision. It answers per-charger questions only and silently forfeits every fleet-wide one.
- **OpenSearch/Elasticsearch, or Postgres full-text, for the line index** — rejected. OpenSearch is a cluster to operate for 175 MB/month. Postgres avoids a new dependency but adds ~5.4M rows and a GIN index to the database ADR 0014 already exists to protect, and still leaves a UI to build. New Relic costs nothing and is already running.
- **Direct-to-S3 presigned upload** — no backend bytes. Rejected: the charger appends a filename to the URL (invalidating the signature), presigned URLs are long and query-heavy for embedded HTTP clients, and S3 presents a CA chain the fleet has not been proven to trust.
- **mTLS / client certificates (OCPP Security Profile 3)** — the AWS IoT / Azure IoT Hub default. Rejected as disproportionate at ~30 chargers with no PKI; see Decision.
- **A bundle-specific throwaway token, decoupled from ADR 0020** — narrower scope, no coupling. Rejected: it requires a fleet-wide provisioning campaign that buys a credential we then throw away, and a second campaign later for the real one.
- **Blocking this feature on ADR 0020 shipping in full** — correct ordering, rejected as disproportionate: it holds a small observability feature hostage to a fleet-wide security migration with its own per-charger burn-down window.
- **An unauthenticated endpoint secured only by an unguessable URL** — rejected outright. An open write target for arbitrary bytes, and "the URL is the credential" has already burned us once (the `qr_payment_{PK}` cross-environment idempotency collision).
- **Short-lived upload URLs issued over the control channel** (the Azure IoT Hub file-upload pattern) — the strongest design, and the natural phase 2. Deferred: it requires the OCPP channel to be authenticated first, which is exactly what this ADR declines to do yet. Nothing here blocks it.

## Still open

This ADR settles transport, authentication, the bundle header contract, delivery semantics, cadence, storage, and the admin surface. What remains is **not** design work but two facts to confirm with the hardware and firmware teams before implementation, both detailed in Consequences: **which modem** these units carry (it decides whether uploads need wrapping in `_mark_ws_drop_expected`), and whether the EEPROM ring buffer's **write head is wear-levelled** rather than kept at a fixed address. Who beyond ADMIN may read Bundles is not yet settled. Retention is now fixed by measurement — 30 days in New Relic, 90 in S3.
