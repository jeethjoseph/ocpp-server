# Customer-facing Asset Code: system-allocated, per-environment series

**Status:** accepted (2026-08-27). Supersedes two uncommitted drafts of this ADR: a 2026-08-07 one deriving the code from a **Bay** (`{prefix}{station:03d}C{bay:02d}`, e.g. `S006C02`), and a same-day one making the code the admin-typed physical stencil. Both are retained below as rejected options because their reasoning is still instructive.

## Context

Two customer surfaces printed `Charger.charge_point_string_id`: the QR landing page (`frontend/app/charge/[id]/page.tsx`) and the `CHARGER ID:` line on the GST invoice PDF (`services/invoice_service.py`). That value is a **UUID4** generated at onboarding — meaningless to a customer, useless to support, and it doubles as the OCPP WSS path segment and the HTTP Basic Auth **username** under [[adr-0020-charger-websocket-basic-auth]], so printing it on a PDF that lands in a stranger's inbox publishes half a credential pair. A third surface, `/my-charges`, showed `Charger.name` — nullable free text with no uniqueness, so `"Charger 3"` could name four different units.

We need one identifier a customer can read off a unit and quote to support, and that support can resolve unambiguously.

One fleet fact constrains the **migration** rather than the design. The hardware is already stencilled: production carries `VOW0001`…`VOW0010` in `Charger.name` — 8 of 13 rows, unique — and staging carries four more (`VOW0001`, `VOW0002`, `VOW0004`, `VOW0005`; the first two duplicating production's). Those stickers exist whether or not the system knows about them, so the backfill must reckon with them even though nothing afterwards does.

## Decision

An **Asset Code**: an environment series plus a zero-padded integer — `VOW0001` in production, `VOWS0001` in staging and development. Regex `^VOWS?\d{4,}$`, stored `VARCHAR(12)`.

- **An alias, not a replacement.** `charge_point_string_id` remains the OCPP identity and auth username; it is scrubbed from customer surfaces and stays visible on admin/franchisee surfaces, where ops needs it for log correlation and firmware deploys.
- **It names the physical unit, not a position.** The code follows the hardware: through a station re-parent, and onto whatever site the unit is installed at. A replacement unit brings its own code rather than inheriting one. This is the direct consequence of the code being *stencilled on the unit* — code and paint cannot disagree, because they are the same fact.
- **Stored, not derived.** A new column `Charger.asset_code`, `VARCHAR(12)`, `UNIQUE NOT NULL`, with a format `CHECK` and an environment-series `CHECK`. The "derive, never store" rule that governs [[adr-0015-ocpi-identity-scheme]]-style identifiers exists to stop a stored string drifting from a mutable parent; here the code derives from nothing mutable — it *is* the row's identity — so the rule has nothing to bite on. Storing it also makes support lookup a plain unique-index hit rather than a parse.
- **System-allocated, never typed.** The server assigns the code at charger creation and it is not an admin-editable field. *(Implementation note, 2026-09-09: allocation is a **Postgres sequence**, not an application-side `max + 1`. `MAX + 1` is a read-modify-write, so two concurrent creates race for the same code — survivable via the `UNIQUE` constraint, but only with a retry wrapped around the entire transaction, because a `UNIQUE` violation aborts the whole Postgres transaction. `nextval` is atomic, so the race and the retry both disappear. Every property this ADR relies on is preserved — system-allocated, never typed, strictly monotonic, never reused — and the one behavioural difference, a burned number when an insert fails, is already sanctioned by the gaps rule below. The sequence sits under a `pre_save` hook so the invariant holds for **every** creation path, not just the admin endpoint.)* Nothing about it derives from `Charger.name`, which stays free-form, nullable and non-unique. This makes uniqueness structural rather than a UX problem: no conflict to prompt about, no availability check to debounce, no typo that can bind a wrong code to a unit. The `UNIQUE` constraint remains as the backstop for concurrent creation.
- **Allocation is strictly monotonic.** A code is **never reused** and gaps are **never backfilled**, including gaps that were never allocated — deliberately simpler than "reuse what is provably free", so nobody has to reason about whether a hole is safe. Production's gaps at `VOW0004`/`VOW0005` therefore persist and its next new unit is `VOW0016`.
- **Per-environment series, validated on write.** `CHARGER_CODE_SERIES` in the git-tracked `backend/policy.py`, keyed on the existing `ENVIRONMENT` var. An unrecognised value resolves to `VOWS`, never `VOW`, so a misconfigured box cannot mint a production-looking code. The series exists because **staging serves real paying customers** (~11 GST invoices/day as of 2026-08), so both registers mint codes a real person reads off a real unit — the same cross-environment hazard that produced the duplicate `VL/F2/` invoice numbers and the `qr_payment_{PK}` refund collision.
- **Minimum width four, not fixed width.** `VOW0001` through `VOW9999`, then `VOW10000` — the register widens by itself, with no migration, no re-padding and no re-stencil at the boundary. Codes are consumed **cumulatively** (a retired unit keeps its code so its historical invoices still resolve), so a fixed ceiling would eventually cost a fleet-wide re-stencil plus a permanent discontinuity in the invoice record. A minimum-width rule removes the ceiling rather than raising it.
- **Lookup parses the integer, not the string.** `VOW0001`, `VOW00001` and `vow1` all resolve to the same unit; a foreign series is rejected rather than coerced. This is what makes the minimum-width rule safe — a code typed at one padding resolves at any other.
- **Every charger has a code, including bench units.** `asset_code` is `NOT NULL` for all rows in the same series; nothing about the code says what a unit is for. The alternative — nullable for `TEST`, with a two-column `CHECK` and a mint-on-promotion path — was rejected on call-site count: 19 admin/franchisee surfaces render charger identity against 3 customer-facing ones, and admin surfaces are exactly where bench units appear, so a nullable code puts a null-branch everywhere it would actually be hit (including the firmware-deploy path, which targets bench hardware constantly) and none of the places it never would. It also revives the disagreeing-fallback problem this ADR exists to end. Promotion stays a single field update.
- **Serviceability is a separate field.** `Charger.purpose` (`PUBLIC` | `PRIVATE` | `TEST`, defaulting `PUBLIC`) carries whether a unit is advertised, billable, and invoiceable. It is deliberately not encoded in the Asset Code: purpose is **mutable** — a bench unit can be promoted to fleet — and an identifier must not change when a mutable attribute changes.
- **A GST Invoice snapshots three facts about the charger.** `charger_id_str` keeps holding exactly what was *printed* — a `charge_point_string_id` UUID before the cutover, an Asset Code after. Two columns join it: `charger_station_id` (the station as of issuance, so a compliance query never parses a string) and `charger_ocpp_id` (the `charge_point_string_id`, retained for audit and **never printed**). The last one preserves the audit link to the physical unit across the cutover.

## Considered options

- **Rename `charge_point_string_id` to the code itself.** Rejected: makes the OCPP identity enumerable, and requires re-flashing every deployed unit's config over flaky Quectel modems — a fleet-wide flag day for a display concern.
- **Derive the code from a Bay** — `{prefix}{ChargingStation.id:03d}C{bay_number:02d}`, e.g. `S006C02`, where a **Bay** is the pair (`ChargingStation`, `Charger.bay_number`) and a swapped-in unit inherits the number. **Rejected**, and this was the 2026-08-07 draft of this ADR. Its argument — that a customer reads the label off the spot, so the code should name the spot and survive a hardware swap — depends on the label being physically at the spot. It is not: nothing prints a bay number on the ground, sticker artwork is produced outside the system, and physical labelling was itself a deferred rollout item. Meanwhile the fleet is *already* stencilled per-unit, so the design paid for swap-stability no physical label would exercise, in the following currency: a hand-verified survey of bay assignments across four production sites; a `StartTransaction` gate whose `bay_number IS NULL` default blocked every customer on any row missed in the backfill; and a public-availability filter that emptied `/stations` and the no-auth map if it shipped before the backfill. Two revenue-outage modes for a display fix. The Asset Code needs no survey, and `purpose` defaults to `PUBLIC`, so a missed row keeps working — the failure direction inverts from fail-closed to fail-open.
- **A `Bay` entity.** Rejected on its own terms even setting the above aside: `Charger.station` is traversed throughout billing, settlements, the station map and the public QR routers, so re-parenting the FK through a new level is large blast radius for 4 stations.
- **Per-station creation sequence** — `VOW-S01-C04`, the format locked at the 2026-07-31 charter grilling. Rejected: it couples the code to the station, so it inherits station PK gaps, changes on re-parent, and after a hardware swap the numbering stops corresponding to anything on the ground — without the compensating benefit the Bay design was reaching for.
- **The admin-typed physical stencil.** A same-day draft made the Asset Code *be* the `VOW####` painted on the unit, entered by an admin at provisioning. Rejected: it buys one genuine benefit — a customer at a dead charger can read the code off the hardware today — at the cost of putting a hand-typed, uniqueness-constrained string on the critical path of charger creation (prompt, availability check, typed `409`, audit-logged corrections), and of binding a customer-facing identifier to `Charger.name`, a field with known dirt (`"VOW0001 "`). System allocation makes uniqueness structural instead. The stencil survives only as the **backfill seed**, for the reason in Consequences.
- **An opaque plate** — Crockford base32, e.g. `VOW-4KQ9`. Held as the fallback if production's `name` column had turned out dirty or non-unique. It is not: all 8 stencilled production rows are clean and distinct, so the stencil wins.
- **An environment letter derived from `ENVIRONMENT`** — `S`/`T`/`D` as a prefix on an otherwise shared numbering. Subsumed: the series does the same job while remaining the string that is physically on the unit.
- **Numeric block partition** — `VOW00001`–`VOW89999` production, `VOW90000`–`VOW99999` staging, mirroring `FRANCHISEE_CODE_BLOCKS` in `policy.py`. Rejected, and the reason matters: the franchisee register uses numeric blocks because **Rule 46(b) caps the invoice serial at sixteen characters** and `F0001/Q/26/00001` spends all sixteen, leaving no room for a distinguishing letter. Blocks there are a workaround for a character budget, not a preferred mechanism. The Asset Code is not part of the serial — it is voluntary descriptive content on the invoice, subject to no statutory length or charset constraint — so it has room for the clearer mechanism. Reusing the *reasoning* (partition the space so two databases cannot collide without coordinating) while rejecting the *workaround* is the consistent choice. A distinct series is also self-evident on a receipt, where `9xxx` means staging only to someone who has been told, and it leaves each register a full range rather than lending 10% of one to an environment that will use about twenty codes.
- **Two booleans, `is_test` and `is_public`,** instead of the `purpose` enum. Rejected: they are not independent — every test unit is non-public — so two free booleans admit `is_test AND is_public`, a bench unit advertised as bookable and drivable-to. The behaviours also fail to decompose: `TEST` gates billing and invoicing, `PRIVATE` gates only visibility.
- **Encoding purpose in the code** via a reserved range (e.g. `VOW9xxx` for bench units), by analogy with `F0000` reserved for VoltLync-owned stations. Rejected: `F0000` works because "VoltLync-owned" is `franchisee_id IS NULL`, structural and permanent. Test-ness is mutable, and an identifier must not change when a mutable attribute does.
- **Renumbering production to close the `VOW0004`/`VOW0005` gaps.** Rejected — see Consequences.
- **Enforcing uniqueness on `Charger.name`.** Rejected at the charter: `name` stays free-form for operator convenience, and uniqueness lives on `asset_code`.

## Consequences

- **The seeded backfill is conditional on verifying the stencils, because `Charger.name` has no integrity guarantee.** It has no write-side validation on either `ChargerCreate` or `ChargerUpdate` — no trim, no format, no non-empty check — it is freely admin-editable, and it has demonstrably drifted (five of thirteen production rows hold non-stencil text; staging holds `"VOW0001 "`). Only one production row carries a corroborating `serial_number`. So the eight fleet rows are checked against the physical labels before the migration trusts them. All clean ⇒ seed, and production needs no re-stencilling. Any mismatch ⇒ start production's sequence at `VOW1001` instead and re-stencil, so a stale sticker resolves to nothing rather than to the wrong unit. The check gates the moment the code first reaches a **GST Invoice**, not the backfill — until then the value lives only in the database and on admin surfaces, where a wrong one is an `UPDATE` rather than a scar. It also needs no dedicated errand: once the admin UI renders the code, comparing it to the label happens during ordinary site work. Prior probability is good — production's 1, 2, 3, 6, 7, 8, 9, 10 and staging's 1, 2, 4, 5 union to a coherent 1–10 register whose gaps are explained, which is what a maintained register looks like rather than a drifted one.
- **The backfill applies an explicit map keyed on `charge_point_string_id`, generated offline and baked into the migration — `upgrade()` never reads `Charger.name` at all.** A derivation would re-read a freely-editable field at run time, so what was reviewed and what executes could differ. Under a map they are the same artifact, and the stencil read becomes an offline provenance step rather than a runtime dependency. The UUID is the key because row ids differ per register and can be reused; the map is selected by `ENVIRONMENT` the way migration 50 selects its CHECK predicate, and development allocates sequentially rather than being mapped. Production's eight fleet units keep their painted numbers (`VOW0003` stays `VOW0003`), the five bench units take `VOW0011`–`VOW0015`, and allocation continues monotonically from there. The alternative — pure `id`-order allocation — was rejected on inspection: it shifts six of the eight painted units by one or more, so the sticker reading `VOW0006` would name the unit at SARADHY TOWERS that is painted `VOW0007`. That is a wrong-answer bug for support, not a missing-answer one, and it is worth one `SELECT` in `upgrade()` to avoid. If a future migration ever needs to allocate without consulting the stencils, it must start the production sequence *above* the painted range so a stale sticker resolves to nothing rather than to the wrong unit.
- **Staging's four real units gain a series letter and must be re-stencilled** (`VOW0004` → `VOWS0004`). One site, four labels. The digits are preserved deliberately, so a re-stencilled unit reads back to its old sticker at a glance — the same courtesy `FRANCHISEE_CODE_BACKFILL_OFFSET` extends by mapping franchisee id 5 to `F9005`.
- **Production hardware needs no re-stencilling at all**, because seeding makes the register agree with the paint on day one. That is the whole return on the seeded backfill, and it is why the physical-labelling question stays off this change's critical path.
- **Renumbering production is free only until the first invoice snapshots a code, and never afterwards.** Today `GSTInvoice.charger_id_str` holds a UUID on every issued row, so nothing yet depends on a code being stable and any renumbering is a pure data edit. After the cutover the column is a frozen snapshot on immutable documents with lazily-rendered, S3-cached PDFs; changing a live row then leaves issued invoices naming a code that resolves to a different unit or to nothing. There is no forward-only variant that avoids this, because the divergence *is* the change.
- **The gaps are not a defect.** `VOW0004`/`VOW0005` are absent from production because those units sit at the staging site. Under monotonic allocation they stay absent, and production's next unit is `VOW00011`. The cost is two numbers out of 99,999.
- **Cross-environment collision is impossible by construction**, not by discipline — enforced by the series `CHECK`, in the spirit of the franchisee blocks ("the previous arrangement relied on nobody creating a colliding franchisee and failed silently for three months").
- **`GSTInvoice.charger_id_str` keeps its name** despite now holding an Asset Code, because it is a header in the GST filings CSV export (`routers/invoices.py`) that feeds an accountant's spreadsheet. The two eras are separable by the code regex. Its two siblings are internal — neither is added to the CSV export, so no saved import mapping changes.
- **Joining an invoice back to hardware goes through `charger_ocpp_id` or the `transaction` FK.** Unlike the rejected Bay design, the Asset Code *does* name a specific unit, so parsing it is not wrong — but the code can be corrected by an admin, and the snapshot cannot. Prefer the columns that were never editable.
- **This ADR takes the opposite position to [[adr-0015-ocpi-identity-scheme]] on derivation, deliberately.** 0015 derives `ocpi_location_id` from the station PK and refuses to derive from `Charger.id` because hardware rows churn. Here nothing is derived at all: the identifier is entered from the physical world and stored. Different input, different conclusion — not an oversight.
- **`backend/policy.py` carries a corrected comment.** Its previous text explained the franchisee blocks as avoiding an environment letter because "the serial is a Rule 46(b) statutory field and staging has no business on a tax invoice", contrasting a then-env-prefixed Charger Code as "a display alias with no statutory meaning". The first half fused a statutory fact (the 16-character cap) with an authoring judgement; the second understated the Asset Code, which reaches two compliance surfaces (the invoice PDF and the filings CSV) even though it is not itself a statutory field. The corrected comment gives the real reason: no room for a letter there, room for one here.
- **Two things this does not solve, both now independent and shippable on their own schedule.** Physical labelling beyond the stencils that already exist is unchanged. And the `StartTransaction` serviceability gate and the public-availability filter now hang off `purpose` rather than off the identifier — including the five production test units currently inflating `total_chargers` on `/stations` and the no-auth map, which `purpose = TEST` fixes when that filter ships.
